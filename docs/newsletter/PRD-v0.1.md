## 1. 目标与成功定义

为 YouTube [@dalei2025](https://www.youtube.com/@dalei2025) 的观众提供免费的中文 AI 实践邮件。观众自愿提交邮箱并确认后，每日收到短小、可行动、有证据的内容；有合适的相关公开视频时附上链接。以持续有用建立关系，不以频道订阅者数量冒充已同意的邮件名单。

首期验证两周：能否吸引确认订阅、带来有意义的回复与视频点击，且用户理解每日频率和退订方式。没有预设产品市场匹配、收入或增长承诺。

## 6. 页面与内容

页面顺序：作者/主站入口 → 价值承诺和表单 → 一封完整示例 → 内容规则和 FAQ → 隐私/退订说明。

品牌方向：中文读者的克制编辑风格，复用主站暖纸色与墨色，移动优先；设计参数 `DESIGN_VARIANCE 5 / MOTION_INTENSITY 2 / VISUAL_DENSITY 3`。不需要额外动画或外部字体请求；示例信本身是核心展示。

每封约 300–500 中文字。结论、原理、判断、动手练习和证据来源为必需，相关视频为可选：

- 一个结论：读完可以记住什么。
- 一个原理：为什么，适用边界是什么。
- 一个判断：什么情况下值得做，什么情况下不适合。
- 一个动手练习：小任务、输入和验收方式。
- 证据来源：官方资料/自有公开视频，标原内容日期和核查日期。
- 相关视频（可选）：有合适相关视频时附上已核实链接；`video_url` 允许为空。没有合适视频的邮件，仍可凭有效干货、动手练习和可靠来源通过审核，不因“待配视频”阻塞整封；不捏造链接。

新视频不要求每日发布。旧经验标日期；素材不足时延后或使用明确标日期的旧经验，不能编造实测。仅使用潘雷自有或有权公开的内容，排除 HP 内部资料、私人邮件、付费课程原文。此版示例是原创方法演示，不宣称某模型性能或作者实测结果。

## 7. 订阅、确认与隐私流程

真实路径候选：观众阅读用途 → 首页 Inline Form 填邮箱 → Kit 接收 → 通用待确认提示 → 邮箱中点击 Kit 确认链接 → Kit 确认活跃状态并跳转公开实战卡页（含第一课）→ 每日已审核邮件 → Kit 退订。

第一课和资源放在公开页，候选路径 `/newsletter/first-ai-card` 集中配置于 `newsletter/paths.ts`。普通公开 URL、查询参数或前端按钮不是确认凭据，访问资源页不代表邮箱确认。工程内欢迎 demo 必须持续标演示，不能把 `?confirmed=true` 当真实验证。真实确认能力和确认邮件的后续跳转用测试账号验收后才能上线。不承诺 Kit Free 的独立自动欢迎序列。

| 情况 | 给读者的反馈 | 处理规则 |
|---|---|---|
| 无效邮箱 | 指明格式错误，保留焦点 | 不发请求 |
| 请求处理中重复点按 | 正在处理，禁用重复提交 | 单次执行，允许取消 |
| 有效提交 | 通用“请按邮箱中说明确认” | 不告知该地址是否已订阅 |
| 重复地址/已确认地址 | 同样通用提示 | 不公开名单状态；由 Kit 去重 |
| 未确认 | 不进入每日活跃名单 | 提示检查垃圾箱；真实重发行为按 Kit 当前功能核验 |
| 已退订再次提交 | 同样通用提示 | 必须重新证明同意，不能本地强制恢复活跃 |
| 网络/服务故障 | 说明未完成、稍后重试 | 不假报成功，不记邮箱日志 |
| 未配置 | 明确演示，不收集真实地址 | 无 Kit 请求；刷新清空演示状态 |

Kit 为名单、确认和退订的唯一来源。仓库只保存公开内容与非个人配置；不保存邮箱、订阅者导出、确认 token、退订 token、API key。避免邮箱进入 URL、前端分析、错误监控和 Notion。来源仅用受控 campaign/source 标识，不加邮箱或个人 ID。网站分析不记录输入框值。

上线前用户需核实发件/回复地址、联系渠道、平台隐私披露和邮寄地址等实际必要字段；本地页面不能捏造这些身份信息。发件域认证只照平台生成的记录操作，保留现有 MX，不能推测 DNS 值。

## 8. 每日内容与人工审核流程

每批准备 7 封 → 用户审核内容、日期、证据，以及附上时的视频 → 7 个 Kit broadcasts 分别排期 → 用户复核时间/人群 → Kit 发信 → 查看失败、退信、退订/投诉和回复。

默认时区 `Asia/Shanghai`；具体钟点待用户决定。[官方排期指南](https://help.kit.com/en/articles/4375330-how-to-schedule-a-broadcast-in-advance) 支持账户时区排期；按收件者当地时区发送需付费，P0 不依赖它。每日一封是用户已经明确提出的需求，不再重复请求批准频率。上线前仍需确定具体钟点、复核实际发送人群，并获得实际平台发送启用授权；每日需求不等于已经启用真实发送。

状态定义：`draft` 草稿 → `reviewed` 用户已审核 → `scheduled` 平台已确认排期 → `sent` 平台确认已发送；执行异常为 `failed`，保留最后已确认状态。编辑已审核内容必须回到草稿；已排期内容改动需撤回/更新排期并重新审核。

P0 使用 Kit 界面管理状态，不构造虚拟控制台。P1 才考虑非 PII 内容台账：`issue_id`、`revision`、`content_date`、`source_urls`、`video_url`（可选，可为空）、`reviewed_by/at`、`send_at+timezone`、`broadcast_id`、`status`、`last_error_code`。未知执行结果先按 broadcast ID 只读查询，禁止盲目再次创建/发送。去重键为 `issue_id + revision + recipient_segment + send_at`；“已发送”只能根据平台回执。
